# Workflow 完整方案

设计基线日期：2026-10-21。状态：待实施的工程方案。最近决策：规格系统自研，OpenSpec / Spec Kit 仅提供方法参考，不嵌入任何一方的实现。

## 1. 定位

Workflow 是“规格驱动 + 原生 Agent 协作 + 证据与恢复”的本地开发工具。安装到项目后，团队可通过统一指令组织变更，而不必为每个项目重写角色、阶段、恢复规则和安装脚本。

用户只安装 Workflow；规格创建、校验、场景追踪、正式规格更新和归档均由内部模块完成。无需规格服务器、数据库、OpenSpec CLI 或 Spec Kit CLI。

## 2. 产品组成

| 部分 | 作用 | 主要交付 |
| --- | --- | --- |
| 规格引擎 | 定义预期行为，管理正式规格与变更增量 | 解析、ID 检查、场景、追踪、冲突检测、归档事务 |
| 工作流规则 | 定义谁执行什么、何时能前进 | 阶段、角色任务、权限范围、重试与挂起策略 |
| 运行工具 | 保存证据，跨会话恢复 | 状态、锁、指纹、事件、恢复计划、集成检查点 |
| 安装套件 | 将共用能力接入不同项目与宿主 | CLI、共享 Skill、宿主薄壳、配置、升级和卸载 |

主会话是唯一 Leader。原生子 Agent 负责设计、实现、测试、审查等工作。确定性工具不调用模型，不自动回答产品方向问题。

首批优先适配 Codex、Claude Code、OpenCode、pi。在任一宿主中，当前主会话直接调用该宿主原生子 Agent 机制；Node.js runtime 仅运行规格、状态、验证、安装和集成工具，不启动 Agent CLI、模型 SDK 会话或外部 Agent runner。能力未知或不满足的宿主保留适配目标状态，先停在门禁并给出依据，不能改用进程包装器补齐。

## 3. 一次变更的闭环

```text
初始化项目
  → 主会话准备独立变更分支和干净 worktree
  → 创建 change 与 proposal
  → 明确规格、验收场景并记录用户授权范围
  → Architect 完善设计、任务与验证计划
  → spec-gate：结构、引用、依赖和审批指纹检查
  → Dev：适用任务内 Red → Green → Refactor，授权范围内实现
  → Tester：场景到验证证据的映射
  → Reviewer：独立只读审查
  → Verify：按受影响范围执行项目验证计划
  → Integrate：规格归档事务、归档后最终检查、提交、可选 PR/CI/合并
  → 核实最终本地或远端事实，标记完成
```

用户对范围的授权可在启动前或当前会话提供，按原始授权及指纹记录。Architect 在范围内细化设计不要求重复批准；引入新行为、范围或违反项目规则则返回用户决策。规格可修订，但受影响下游证据必须失效，不能以阶段完成为由冻结错误规格。

子 Agent 使用绑定 run/dispatch/attempt 的版本化 JSON 回报；适用验证命令、CI 映射和跳过理由进入证据。独立审查覆盖完整变更，修复使相关审查/验证失效；归档后重新验证最终工作树，失败可受控 reopen。修复预算跨重新归档和后继 run 保留。项目可用确定性检查脚本表达不变量，但通用引擎不固化项目栈命令。

## 4. 关键设计选择

1. 单仓库、单安装包、TypeScript + ESM；目标运行环境 Node.js 22.12+ 与 Git。
2. 自研规格协议 `formatVersion: 1`。Markdown 承载可阅读内容，YAML front matter 承载严格元数据。
3. `.workflow/` 是接入项目的数据根，配置、正式规格、变更、归档及 Epic 受 Git 管理。
4. 运行状态存入主仓共享 Git 元数据下的 `workflow/`，多 worktree 共用且不进入业务提交。
5. `state.json` 是机器运行状态的唯一权威源，`progress.md` 是可重建视图。
6. 需求、场景和任务使用稳定 ID；通过显式引用建立追踪，不能仅比较文案或任务勾选。
7. 默认 local profile 不要求 GitHub；github profile 管 PR/required CI/远端完成事实。独立 tracking 适配管事项来源，先支持 GitHub Issues，可与任意仓库 profile 组合。
8. 安装生成共享资产和宿主入口，记录版本与内容摘要；升级采用三方比较和可恢复写入。
9. 原生 Agent 的派发由主会话完成；CLI 负责准备任务、校验阶段和持久化，不建立第二个 Agent 编排进程。

## 5. 工程与项目数据

源码按 `spec / workflow / runtime / project / repository / hosts / installer / cli` 分组。角色、协议和模板位于 `assets/`，由安装器按精确版本部署到目标项目。

目标项目保留一份 `.workflow/config.yaml`，其中配置源码范围、权威文档、角色映射、命令和集成策略。不同技术栈通过配置表达，核心中不识别 MusicTag、Tauri、Rust、Vue 等项目特例。

正式规格为 `.workflow/specs/<capability>/spec.md`。活动变更位于 `.workflow/changes/<change>/`，包含 proposal、规格增量、design、tasks 和元数据。归档结果位于 `.workflow/archive/<date>-<change>/`。详细格式见 [规格规范](03-specification.md)。

[TDD 与交付契约](14-tdd-and-delivery.md)定义任务测试方式、先测试证据、规格归档及 Git 顺序。代码、测试、正式规格与归档通过同一变更分支/PR 交付；归档前同步 base 并重验，归档后最终检查通过才提交归档并推进合并。中间开发提交由主会话审计后发起，不要求为每个 TDD 颜色单独提交。后续行为修订使用新 change；Git/CI 策略变更同样进入规格适用性、设计和验证计划检查。

## 6. 安装与使用

先以 npm 单包发布，包名可带发布者 scope，统一命令名保持 `workflow`。初次全局安装提供 CLI；`workflow init` 将必要资产和精确版本项目本地 runtime 一起物化。宿主入口调用项目本地 runtime，避免全局升级悄悄改变既有项目。

构建时把可打包的运行依赖纳入产物；安装完成后的本地规格与状态命令不联网，也不再动态执行 npx 下载。普通解析库不影响产品独立性；具体依赖与许可证在实现阶段锁定和记录。

## 7. 交付范围

首个可用版本包括：单项目、单变更、自研规格、local 集成、共享执行协议、Codex/Claude Code/OpenCode/pi 四个首批宿主的入口设计及能力探测、安装升级卸载、恢复与事务验收。只有真实安装、原生派发与角色能力通过契约检查的宿主才标为可执行。宿主能力调查未通过时明确 unverified/unsupported，不以 Node.js 或 Agent CLI 启动角色作为替代。

后续在相同架构上分别交付项目管理事项适配（先 GitHub Issues 只读）和 GitHub 仓库集成，再补 Epic worktree 并行及旧规格导入工具。二者独立实施与验收，细节见 [事项适配](15-tracking-adapters.md)。完整方案包含这些契约；里程碑明确哪些先交付。暂不建设在线调度服务、插件市场、任意工作流 DSL、跨仓事务或自托管模型网关。

## 8. 实施与验收

按 [实施计划](10-roadmap.md) 依赖推进，首先使规格引擎在纯 fixture 中可校验和安全归档，再接入状态、宿主与安装闭环。发布以打包产物在空项目中的安装及恢复验收为准，不能只验证源码仓中的直接运行。

关键失败验收包括：规格基线冲突、已通过验证后的源码变更、被中断的安装/归档、会话锁误接管、CR 写文件、升级时用户改动、缺失宿主能力、伪造/陈旧远端完成事实。
