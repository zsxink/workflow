# 产品需求

## 1. 用户与场景

面向在不同代码仓中使用 Agent 的个人和团队。现有痛点是流程指令散落、规格与任务无关联、阶段完成缺少事实、切换会话后恢复不可靠，以及安装后无法安全升级。

用户故事：维护者一次安装接入项目；需求方审阅规格并授权范围；主会话按依赖派发；开发者只修改授权路径；审查者独立检查；新会话通过工具恢复；项目升级后保留自己的配置和修改。

## 2. 功能需求

| ID | 需求 | 可验收结果 |
| --- | --- | --- |
| REQ-PRODUCT-001 | 项目独立 | 在不同目录和两种技术栈 fixture 中运行，不读取原 MusicTag 仓库 |
| REQ-PRODUCT-002 | 自研规格 | 未安装 OpenSpec/Spec Kit 且离线时创建、校验、计划同步及归档 |
| REQ-PRODUCT-003 | 统一安装 | 一个包安装 CLI、共享协议、角色与所选宿主入口 |
| REQ-PRODUCT-004 | 追踪 | 每条新增/更新需求有场景，每个行为任务引用需求，每个场景有验证映射 |
| REQ-PRODUCT-005 | 阶段门禁 | 缺少必需证据、审批或当前指纹时禁止成功状态及集成 |
| REQ-PRODUCT-006 | 原生协作 | 优先适配 Codex/Claude Code，OpenCode/pi 后续适配；主会话使用宿主原生方式派发，任务含角色/范围/基线/验收；无 Node.js Agent runner、Agent CLI 或外部会话驱动 |
| REQ-PRODUCT-007 | 范围控制 | 原范围内技术选择由主会话处理；范围变化需记录新授权并使下游失效 |
| REQ-PRODUCT-008 | 中断恢复 | 新会话读取当前 Git/文件事实，形成下一步计划，陈旧成功不复用 |
| REQ-PRODUCT-009 | 安装生命周期 | 重复安装幂等；升级不覆盖用户改动；卸载不删除规格与运行证据 |
| REQ-PRODUCT-010 | 本地闭环 | 无 GitHub 账号或网络也可完成本地规格、开发、验证、归档与提交 |
| REQ-PRODUCT-011 | 可选远端集成 | github profile 查询真实 PR/required CI 与合并事实，重复恢复不重复建 PR；不要求事项来源同为 GitHub |
| REQ-PRODUCT-012 | Epic | 子变更独立分支/worktree；前置集成事实满足后才能调度后继 |
| REQ-PRODUCT-013 | 严格配置 | 未知字段、越界路径、重复 ID、无效命令被确定性检查拒绝 |
| REQ-PRODUCT-014 | 宿主能力 | 入口安装成功与执行能力就绪分开显示；只读能力不足不报告完整可用 |
| REQ-PRODUCT-015 | 结构化任务回报 | 子 Agent 回报按版本化协议校验；缺字段、越界路径或无证据成功不能推进阶段 |
| REQ-PRODUCT-016 | 适用验证与最终复核 | 验证计划按变更影响和项目 CI 契约确定并记录跳过理由；修复后受影响证据失效；归档后最终检查通过才可提交归档并集成 |
| REQ-PRODUCT-017 | 任务内 TDD | 可自动验证的新增/变更行为和 Bug 修复先记录有效 Red，再以同一测试通过 Green 与重构检查；缺失或伪造顺序证据时任务不能完成；例外须在 spec-gate 明确审查 |
| REQ-PRODUCT-018 | 规格与 Git 一起交付 | 代码、测试、正式规格更新与归档内容通过同一分支/PR 集成；归档落盘、提交、合入分别核实，未集成归档失败可恢复，已集成规格通过新 change 修订 |
| REQ-PRODUCT-019 | 独立事项来源 | tracking 适配与 repository 集成可独立组合；先支持 GitHub Issues 只读接入，核实身份/输入快照；事项状态不代替授权或集成事实 |

门禁承诺限于 Workflow 管理的状态及动作；宿主工具的越界阻断按实际能力报告，不承诺防御恶意本地主机或绕过 CLI 的所有写入。详见 [宿主强制范围](09-hosts.md)。

## 3. 通用性要求

不能把 backend/frontend/both 固定为 Rust/Vue，也不能用文件路径中的项目名截取相对路径。模块分类是项目配置中的任意稳定 ID，例如 api、web、docs。

权威文档、分支基线、验证命令、构建产物路径、事项连接与关联要求、提交策略均由项目配置。事项来源适配与代码仓库集成独立，详情见 [事项适配](15-tracking-adapters.md)。工具可给模板，但不通过猜测自动执行未知项目命令。

## 4. 数据和可用性

配置、规格和任务应能用普通文本编辑器查看；机器元数据有版本和明确错误定位。一次命令的 JSON 输出须可供 Agent 消费，不能让 Agent 从终端颜色或提示文字猜状态。

工具不存储模型 API key，不主动连接模型供应商。运行记录仅保留恢复必需的命令、结果摘要和事实，证据中环境值应脱敏。相对路径允许项目搬迁；worktree 事实在恢复时重新解析。

## 5. 质量门禁

结构校验不等于需求正确；`validate` 负责语法、引用、依赖和所需字段，人工/Agent 负责语义、范围与可测试性判断。相关结论分别记录，不把解析通过写成产品批准。

Agent 自报是待核实声明，命令、Git 和权限事实必须由相应工具采集。验证计划应依据项目声明、本次变更影响和适用 CI 选择检查项，未执行项要有理由；通用引擎不硬编码项目技术栈。独立审查覆盖固定基线到最终工作树的全部变更路径。修复不得沿用已失效的 CR/Verify 证据；预算跨恢复、重新归档和后继 run 保留，耗尽后挂起。归档后的最终工作树必须重新执行所选命令、核查规格投影和接受独立审查；失败时通过受控 reopen 返回活动变更修复。

每条 requirement 至少一个可观察场景。需要手工验收的项目允许明确配置手工证据；手工验收尚未完成时保持 pending 或 suspended。外部宿主无法提供文件隔离时必须披露能力级别，不能用审计代替事前隔离能力。

## 6. 首版交付判定

先以自用项目试点，在两个真实仓库记录质量、成本、返工与门禁拦截。所有 REQ-PRODUCT-001 至 010、013 至 018 在打包产物 fixture 中成立，优先完成 Codex、Claude Code 的安装契约与显式能力报告；OpenCode/pi 后续适配，不阻塞首个预览。至少一个优先宿主通过完整原生执行及 Reviewer 只读验收才可报告完整闭环；执行可用标记由实际宿主验收决定，不能因列为适配目标就默认通过。011、012、019 在后续里程碑完成前标为计划能力；019 的首个实现仅承诺 GitHub Issues 只读接入。
